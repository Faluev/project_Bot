# Telegram-боты «Сборщик» и «Курьер»

Проект пилотного сервиса экспресс-доставки продуктов.

**Город запуска:** Душанбе, Таджикистан  
**Этап:** пилот на один район  
**Назначение:** на первом этапе вместо мобильных приложений для персонала используются два Telegram-бота. Приложения для сборщика и курьера планируются отдельным этапом.

# 2. Путь заказа по исходному ТЗ

Целевой процесс:

```
Новый
  ↓
Принят
  ↓
Собирается
  ↓
Собран
  ↓
Ожидает курьера
  ↓
В пути
  ├──→ Доставлен
  └──→ Отклонён
```

В текущей реализации бизнес-статусы и переходы централизованы и защищены от недопустимых переходов.

Для операций с заказом дополнительно проверяется:

```
заявка одобрена
      ↓
доступ сотрудника включён
      ↓
сотрудник на смене
      ↓
подходящая роль
      ↓
операция разрешена
```

# 3. Что реализовано сверх исходного ТЗ

В процессе разработки были добавлены функции и защитные механизмы, которых не было сформулировано в исходном ТЗ как отдельные требования.

## Ролевая архитектура

Один Telegram-аккаунт может иметь две независимые записи:

```
telegram_id + picker
telegram_id + courier
```

Доступ, смена и статистика ролей разделены.

## Централизованная работа с текущим сотрудником

Handlers используют единый слой определения текущей роли и сотрудника.

## Машина переходов статусов

Разрешены только предусмотренные переходы заказа. Повторные и недопустимые переходы блокируются на уровне бизнес-логики.

## Защита от гонок

Критические операции выполняются транзакционно. В частности, два сотрудника не могут одновременно корректно закрепить один и тот же заказ.

## Идемпотентность

Повторное одобрение заявки, повторное отклонение заказа и другие повторные операции не должны создавать второе изменение состояния.

## Расширенный аудит

Добавлен отдельный журнал административных событий:

- кто выполнил действие;
- какой заказ затронут;
- старый статус;
- новый статус;
- детали события;
- время.

Доступен раздел **📜 Аудит** и команда `/audit`.

## Автоматическое уведомление администратора о новой заявке

После новой заявки администратор получает сообщение с кнопками:

- **Одобрить**
- **Отклонить**

Повторные уведомления для одной и той же pending-заявки не отправляются.

## Причины отклонения заказа

Для курьера добавлены варианты:

- клиент не вышел / не отвечает;
- клиент отказался;
- неверный адрес;
- другая причина с текстом.

## Backup базы

Есть отдельный скрипт:

```bash
python backup_database.py
```

Он создаёт timestamped-копию SQLite базы в `backups/`.

## Миграция старой БД

Структура сотрудников была изменена без требования удалить существующие данные. Для legacy-базы есть миграция и отдельные тесты.

## Retry Telegram-сообщений

Временные сетевые ошибки повторяются, постоянные ошибки запроса не зацикливаются.

# 3.1. E2E и concurrency/stress тестирование

Для текущего production-аудита добавлены два отдельных контура.

## Concurrency / stress

Файл:

```
tests/test_concurrency_stress.py
```

Он проверяет:

- 20 сборщиков одновременно пытаются забрать один заказ — победитель должен быть только один;
- 20 курьеров одновременно пытаются забрать один заказ — победитель должен быть только один;
- 10 сборщиков параллельно обрабатывают очередь из 20 заказов без дублей и нарушения FIFO;
- курьер с двумя активными заказами не может доставить более новый заказ раньше старого, в том числе при одновременных попытках.

Запуск:

```bash
python -m unittest tests.test_concurrency_stress -v
```

## Реальный Telegram smoke/E2E

Файл:

```
scripts/e2e_two_bots_smoke.py
```

Скрипт запускает **оба реальных процесса**:

```bash
python bot.py
python courier_bot.py
```

и проверяет через Telegram Bot API, что оба бота действительно поднялись и доступны.

Минимальный запуск:

```bash
python scripts/e2e_two_bots_smoke.py
```

Для проверки реальной отправки сообщений в тестовые чаты:

```bash
E2E_PICKER_CHAT_ID=<picker_chat_id> \
E2E_COURIER_CHAT_ID=<courier_chat_id> \
python scripts/e2e_two_bots_smoke.py --send-smoke
```

На Windows Git Bash команда выше также подходит. В PowerShell используйте:

```powershell
$env:E2E_PICKER_CHAT_ID="<picker_chat_id>"
$env:E2E_COURIER_CHAT_ID="<courier_chat_id>"
python scripts/e2e_two_bots_smoke.py --send-smoke
```

Smoke-runner намеренно не имитирует Telegram callback-кнопки: такие действия должны проверяться реальными тестовыми аккаунтами в Telegram. После успешного старта обоих процессов он выводит последовательность production E2E-сценария:

```
регистрация
→ approve
→ начало смены
→ новый заказ
→ сборка
→ уведомление курьера
→ pickup
→ delivery
→ reject
→ решение администратора
→ строгий FIFO на нескольких заказах
```

Секреты и Telegram-токены в репозиторий не добавляются.

# 10.1. Production-конфигурация

Production-параметры не зашиваются в коде. Они задаются через `.env`; шаблон находится в `.env.example`.

| Параметр | Назначение | Проверка |
|---|---|---|
| `BOT_TOKEN` | токен бота сборщика | обязателен, не пустой |
| `COURIER_BOT_TOKEN` | токен бота курьера | обязателен, не пустой |
| `ADMIN_TELEGRAM_ID` | Telegram ID администратора | обязателен, положительное целое |
| `DATABASE_PATH` | путь к SQLite | абсолютный или относительно проекта |
| `BACKUP_PATH` | каталог резервных копий | абсолютный или относительно проекта |
| `LOG_LEVEL` | уровень логирования | `DEBUG/INFO/WARNING/ERROR/CRITICAL` |
| `TIMEZONE` | часовой пояс runtime/backup | проверяется через IANA ZoneInfo |
| `ORDER_TIMEOUT_MINUTES` | операционный таймаут | положительное целое |

Перед production-запуском нужно проверить:

1. токены не являются значениями из `.env.example` и не попали в Git;
2. `ADMIN_TELEGRAM_ID` соответствует реальному аккаунту администратора;
3. `DATABASE_PATH` указывает на постоянное хранилище;
4. `BACKUP_PATH` находится на диске с достаточным свободным местом и правами записи;
5. `LOG_LEVEL` выбран осознанно — обычно `INFO`;
6. `TIMEZONE` соответствует операционной зоне проекта;
7. `ORDER_TIMEOUT_MINUTES` соответствует реальному SLA пилота.

Секреты не выводятся в логи и не должны передаваться через аргументы командной строки.

## 10.2. SQLite: текущая граница и roadmap

SQLite остаётся основной БД текущего пилота. Миграция только ради архитектурной «красоты» сейчас не требуется.

Ограничения, которые нужно учитывать при росте:

- одна SQLite-база является общей точкой записи для двух bot-процессов;
- конкурентные операции уже защищены транзакциями, но рост количества записей и длительности транзакций увеличит contention;
- горизонтальное масштабирование нескольких экземпляров ботов с общей БД потребует отдельной инфраструктурной проверки;
- будущие API/web-admin и более высокая частота конкурентных операций будут естественным кандидатом на PostgreSQL.

### Этап миграции на PostgreSQL

Миграцию делать отдельной задачей, когда появится реальная потребность. План:

1. выделить repository/data-access слой из прямых SQLite-вызовов;
2. зафиксировать SQL-независимый контракт бизнес-операций;
3. выбрать PostgreSQL и схему миграции данных;
4. добавить интеграционный тестовый контур с PostgreSQL;
5. выполнить миграцию `delivery.db` с проверкой количества заказов, сотрудников и audit events;
6. провести concurrency/regression suite на PostgreSQL;
7. только после этого переключить production.

До миграции текущий SQLite-пилот должен сохранять транзакционную защиту, backup и регрессионные тесты.

## Ключевой принцип проекта

Telegram-боты являются интерфейсом для сотрудников.

Бизнес-логика, состояния заказа, права доступа, история и аудит должны оставаться защищёнными на уровне серверной логики и базы данных, чтобы пользователь не мог нарушить процесс простым повторным нажатием кнопки.
