# Контракт жизненного цикла заказа

Этот документ фиксирует официальный контракт жизненного цикла для текущего Telegram-пилота и границу интеграции с будущим клиентским приложением/API.

## 1. Принцип

**Статус заказа** — текущее бизнес-состояние заказа.

**action_log** — неизменяемый журнал событий: кто, что и когда сделал, с каким переходом статуса и дополнительными деталями.

Не следует превращать каждое пользовательское событие в отдельный DB-статус без необходимости.

## 2. Текущая машина статусов Telegram-пилота

```
new
  |
  | Сборщик нажал «Начать сборку»
  v
assembling
  |
  | Сборщик нажал «Заказ собран»
  v
awaiting_courier
  |
  | Курьер нажал «Забрал заказ»
  v
in_delivery
  |-------------------|
  |                   |
  v                   v
delivered          rejected
                      |
                      | Администратор фиксирует решение
                      v
              return_to_stock / write_off
              (статус остаётся rejected)
```

Разрешённые переходы:

| Текущий статус | Действие | Следующий статус | Кто выполняет |
|---|---|---|---|
| `new` | Начать сборку | `assembling` | Сборщик |
| `assembling` | Заказ собран | `awaiting_courier` | Сборщик |
| `awaiting_courier` | Забрал заказ | `in_delivery` | Курьер |
| `in_delivery` | Доставлено | `delivered` | Курьер |
| `in_delivery` | Отклонить + причина | `rejected` | Курьер |
| `rejected` | Вернуть на склад | `rejected` | Администратор |
| `rejected` | Списать | `rejected` | Администратор |

Для `return_to_stock` и `write_off` изменение статуса не требуется: это решения по результату отклонённого заказа, которые фиксируются в `action_log`.

## 3. События и история

Ключевые события текущего процесса:

| Событие | Статус до | Статус после | Смысл |
|---|---|---|---|
| `start_assembly` | `new` | `assembling` | Сборщик принял заказ в работу и начал сборку |
| `complete_assembly` | `assembling` | `awaiting_courier` | Сборка завершена, заказ передан на этап ожидания курьера |
| `pickup_order` | `awaiting_courier` | `in_delivery` | Курьер забрал заказ |
| `deliver_order` | `in_delivery` | `delivered` | Курьер подтвердил доставку |
| `reject_order` | `in_delivery` | `rejected` | Курьер отклонил заказ с причиной |
| `return_to_stock` | `rejected` | `rejected` | Администратор решил вернуть товар |
| `write_off` | `rejected` | `rejected` | Администратор решил списать товар |

Для каждого изменения состояния сохраняются старый статус, новый статус, действие, исполнитель и время.

## 4. Как текущая модель соответствует исходному ТЗ

Исходное ТЗ описывает более детальную последовательность:

```
New
  ↓
Accepted
  ↓
Assembling
  ↓
Assembled
  ↓
Awaiting courier
  ↓
In delivery
  ├── Delivered
  └── Rejected
```

В текущем Telegram-пилоте два этапа ТЗ намеренно не представлены отдельными DB-статусами:

- **Accepted** объединён с фактическим принятием заказа сборщиком и переходом `new → assembling`.
- **Assembled** объединён с завершением сборки и переходом `assembling → awaiting_courier`.

Это сделано потому, что данный репозиторий реализует интерфейсы сотрудников, а клиентское приложение и его API находятся за пределами репозитория.

## 5. Контракт для будущего Client App/API

При создании клиентского API не следует автоматически переносить каждый внутренний DB-статус один в один.

Внешний контракт должен позволять сообщать как минимум:

- текущее состояние заказа;
- номер заказа;
- время изменения;
- ключевое событие;
- при необходимости — данные об исполнителе/этапе.

Например:

```json
{
  "order_number": "TEST-0001",
  "status": "assembling",
  "event": "start_assembly"
}
```

Таким образом клиент может показать пользователю понятное состояние:

> 📦 Заказ принят в работу

а затем:

> 🛒 Заказ собирается

не требуя отдельного DB-статуса `accepted`.

Аналогично завершение сборки может быть представлено событием `complete_assembly` при статусе `awaiting_courier`.

## 6. Почему сейчас не добавляем accepted/assembled в БД

Добавление двух статусов без готового контракта Client App/API потребовало бы одновременно менять:

- машину переходов;
- обработчики сборщика;
- таймауты;
- уведомления;
- админскую ленту;
- историю;
- тестовые данные;
- существующие тесты;
- будущую интеграцию клиента.

Для текущего Telegram-пилота это не даёт самостоятельной функциональной ценности.

Если клиентское приложение потребует отдельные публичные состояния `accepted` и `assembled`, это должно быть отдельным изменением версии API/бизнес-контракта с миграцией и регрессионными тестами.

## 7. Правила безопасности жизненного цикла

1. Любой переход статуса проходит через `ORDER_STATUS_TRANSITIONS`.
2. Повторное нажатие кнопки не должно повторно менять состояние.
3. Сборщик должен быть одобрен, активен, находиться на смене и иметь роль `picker`.
4. Курьер должен быть одобрен, активен, находиться на смене и иметь роль `courier`.
5. Сборщик может завершить только назначенный ему заказ.
6. Курьер может доставить или отклонить только назначенный ему заказ.
7. Отклонение требует непустой причины.
8. Решение по отклонённому заказу можно принять только один раз.
9. История действий не заменяется текущим статусом.
10. Админская панель отражает процесс и предоставляет необходимые административные решения, но обычный путь заказа выполняется сотрудниками.

## 8. Граница текущего проекта

Сейчас в репозитории находятся:

- Telegram-бот сборщика;
- Telegram-бот курьера;
- SQLite;
- Telegram-панель администратора;
- бизнес-логика заказа;
- история и аудит.

За пределами текущего репозитория остаются:

- клиентское приложение;
- полноценный API для клиентского приложения;
- мобильные приложения сборщика и курьера;
- отдельная web-админка.

Поэтому этот документ является контрактом текущего Telegram-пилота и основой для следующего этапа API.


## 9. Строгая очередь курьера

Курьер получает заказ сразу после перехода `assembling → awaiting_courier`. Ожидание второго заказа не допускается.

1. Максимум одновременно в доставке — **2 заказа**.
2. Если доступен только один заказ — он сразу отправляется курьеру.
3. Если курьер уже взял один заказ, второй старый ожидающий заказ может быть выдан ему сразу.
4. Пока у курьера есть хотя бы один ранее взятый заказ со статусом `in_delivery`, новые ожидающие заказы ему не выдаются.
5. Курьер доставляет свои уже взятые заказы строго по времени создания: сначала более старый, затем более новый.
6. Расстояние до клиента не влияет на порядок доставки.
7. После доставки последнего ранее взятого заказа следующий самый старый `awaiting_courier` заказ отправляется этому курьеру автоматически, без нажатия `🚚 Текущий заказ`.
8. Один и тот же заказ не должен повторно уведомляться одному курьеру.
9. Если другой курьер забрал заказ, устаревшая карточка удаляется у остальных курьеров.
